# Форум: как включить

Форум написан целиком и работает прямо сейчас — но в черновом режиме, где
записи видны только в одном браузере. Чтобы их увидели другие люди, нужна
общая база. Ниже как её подключить: примерно двадцать минут, денег не стоит,
карта не нужна.

## Почему без базы нельзя

Сайт статический: GitHub Pages отдаёт файлы и ничего не принимает. Пост,
комментарий и лайк надо где-то сохранить, а сохранять некуда — это не
недоделка, а свойство бесплатного хостинга.

Выбран **Supabase**: он даёт Postgres, к которому страница обращается прямо
из браузера, и готовую систему входа. Своей серверной части у проекта
не появляется, платить по-прежнему нечему.

## Порядок подключения

### 1. Создать проект

[supabase.com](https://supabase.com) → войти через GitHub → **New project**.

- Имя: любое, например `zroute-s33`.
- Пароль базы: придумать и **сохранить** — он понадобится, если однажды
  полезешь в базу напрямую. Для сайта он не нужен.
- Регион: ближайший к аудитории, например Frankfurt.
- План: **Free**.

Проект собирается пару минут.

### 2. Выключить подтверждение почты

**Это обязательный шаг, без него регистрация не заработает.**

Вход у нас по нику и паролю, почты нет вовсе — так решено осознанно
(см. `config.js`). Ник превращается в адрес вида `ник@users.zroute-s33.local`,
домен вымышленный, письма туда никто не отправляет и получить их нельзя.

Если подтверждение оставить включённым, регистрация будет ждать письма,
которое никогда не придёт.

**Authentication → Sign In / Providers → Email**:

- **Confirm email** — выключить.
- Остальное не трогать.

### 3. Создать таблицы

**SQL Editor → New query** → вставить содержимое
[`supabase/schema.sql`](../supabase/schema.sql) целиком → **Run**.

**Ничего в нём не правь.** Файл рассчитан на то, что его вставляют как есть.
Правка внутри комментария рвёт строку, её хвост остаётся без `--` и становится
настоящим SQL — запуск падает с невнятной ошибкой в конце, хотя со схемой всё
в порядке. Одноразовые действия, где нужно подставить свой ник, лежат
в отдельных файлах: `first-admin.sql` и `cleanup-test-data.sql`.

Скрипт можно запускать повторно: на уже созданном он не падает, а недостающее
добавляет. **Если схема выполнялась раньше, запусти её ещё раз** — в ней
исправлены ошибки, из-за которых лента оставалась пустой и не работала правка
постов (подробности ниже, в разделе «Что было сломано»).

Что именно он настраивает:

| Что | Зачем |
|---|---|
| Права на строки (RLS) | Без них публичный ключ давал бы полный доступ к таблицам |
| Автора подставляет база | Подделать авторство или чужой ник запросом мимо сайта нельзя |
| Одна реакция на человека | Лайк и дизлайк разом невозможны по устройству таблицы |
| Удаление = отметка | Пост остаётся заглушкой с причиной, а не исчезает молча |
| Функции входа и восстановления | Служебный ключ не покидает базу |

### 4. Прописать ключи в config.js

Нужны две строки: адрес проекта и публичный ключ. Лежат они, к сожалению,
**на разных страницах** — Supabase их развёл, и это первое место, где обычно
застреваешь.

#### 4.1. Адрес проекта

Самый надёжный способ — **собрать из адресной строки**, он не зависит
от того, как в очередной раз переставят меню.

Открой свой проект и посмотри на адрес в браузере:

```
https://supabase.com/dashboard/project/abcdefghijklmnopqrst
                                       ^^^^^^^^^^^^^^^^^^^^
                                       идентификатор проекта
```

Адрес для конфига собирается из него:

```
https://abcdefghijklmnopqrst.supabase.co
```

Два других способа, если хочется скопировать готовое:

- Кнопка **Connect** наверху страницы проекта — показывает адрес и ключ разом.
- **Settings → Data API** → строка **Project URL**.

На странице **Settings → API Keys** адреса нет: там только ключи.

**Про хвост `/rest/v1/`.** В разделе Data API адрес показан вместе с ним —
это готовый путь к таблицам, а не адрес проекта. Нужен только корень:

```
берём:      https://abcdefghijklmnopqrst.supabase.co
не берём:   https://abcdefghijklmnopqrst.supabase.co/rest/v1/
```

Причина в том, что от корня отходят **две** ветки: `/rest/v1` — к таблицам,
`/auth/v1` — ко входу. Сайт дописывает нужную сам, поэтому с хвостом
получилось бы `/rest/v1/rest/v1/…`, а вход не нашёлся бы вовсе.

Но если скопируешь с хвостом — ничего не сломается: сайт отрежет его сам.
Так же он поступит с лишней косой чертой на конце и с `/auth/v1/`. Скопировать
ровно то, что написано на странице, — нормальное поведение, и наказывать
за него непонятной ошибкой неправильно.

#### 4.2. Публичный ключ

**Settings** (шестерёнка внизу левого меню) → **API Keys**.

Годится любой из двух видов:

| Вид | Как выглядит |
|---|---|
| Новое поколение | `sb_publishable_…` |
| Прежнее | длинный `eyJhbGci…` с подписью **anon** или **public** |

Работают одинаково, бери тот, который видишь у себя.

**Чего брать нельзя.** Рядом лежит второй ключ — `sb_secret_…` или
**service_role**. Он даёт полный доступ ко всей базе в обход всех правил,
а `config.js` виден в публичном репозитории: такой ключ там означает, что
форум чужой. Названия похожи, и кнопка «копировать» у них одинаковая,
поэтому смотри на подпись.

Если всё же перепутаешь, сайт не станет молча работать со служебным ключом:
форум откажется запускаться и скажет, какой ключ попал в файл. Ошибка,
которая работает, хуже ошибки, которая падает.

#### 4.3. Вписать в config.js

Файл в корне репозитория, раздел `forum` внизу:

```js
forum: {
  source: 'supabase',        // было 'local'

  supabase: {
    url: 'https://abcdefghijklmnopqrst.supabase.co',  // свой адрес
    anonKey: 'sb_publishable_...',                    // свой публичный ключ
    nickDomain: 'users.zroute-s33.local',             // не менять
  },
```

Три вещи, на которых обычно спотыкаются:

- `source` меняется с `'local'` на `'supabase'` — без этого сайт продолжит
  работать в черновом режиме, и никакие ключи не помогут.
- В адресе **нет** косой черты на конце.
- Кавычки одинарные, запятая после строки на месте — это обычный JavaScript,
  и лишняя правка ломает файл целиком.

После правки изменения надо выложить на сайт: закоммитить и запушить в `main`.
GitHub Pages пересоберётся сам за минуту-две.

### 5. Стать администратором

Роль по умолчанию — участник, и назначить администратора может только
администратор. Первого поэтому назначают руками, один раз. Это не лишний шаг:
если бы роль выдавалась по просьбе, её мог бы попросить кто угодно.

**Порядок такой — и порядок важен.**

**5.1. Сначала зарегистрируйся на сайте.** Открой
https://zroutehub.bond/, на вкладке **Форум** введи свой ник
и пароль, нажми **Зарегистрироваться**.

До этого шага в базе нет ни одной учётной записи, и назначать роль просто
некому — запрос ниже ничего не найдёт.

**5.2. Проверь, что запись появилась.** В Supabase: **Table Editor** (иконка
таблицы в левом меню) → таблица **forum_users**. Там должна быть одна строка
с твоим ником и `role = member`.

Если строки нет — регистрация не прошла. Самая частая причина: не выключено
подтверждение почты (пункт 2). Вторая по частоте: `source` остался `'local'`,
и запись ушла в браузер, а не в базу.

**5.3. Выдай себе роль.** Открой файл
[`supabase/first-admin.sql`](../supabase/first-admin.sql), замени в нём
`ТВОЙ_НИК` на свой ник и выполни в **SQL Editor**.

Ник на форуме — это тот, который ты придумал при регистрации. С логином
на GitHub он не связан никак и совпадать не обязан.

Должно появиться `Success. 1 row(s) affected`.

Если написано `0 rows` — ник не совпал. В том же файле, в самом низу, есть
запрос, который показывает всех участников: выдели его строку и нажми **Run**,
потом подставь написание оттуда. Регистр не важен, лишний пробел или другая
буква — важны.

**5.4. Перезайди на сайте.** Выйти и войти снова: роль читается при входе,
и в уже открытой сессии она останется прежней.

После этого в панели (`admin.html`) появятся вкладки **Жалобы** и **Игроки**.

Дальше администраторов можно назначать без SQL — обычным способом, из панели.

## Закрытые чаты альянсов

Чаты живут в тех же аккаунтах, что и форум, и включаются одним файлом:
открой SQL Editor в Supabase, вставь [`supabase/chats.sql`](../supabase/chats.sql)
целиком → **Run**. Запускать после `schema.sql`, `profiles.sql` и
`rich-forum.sql`; повторный запуск безопасен.

### Управление игроками: обязательная цепочка SQL

Кнопки на вкладке **«Игроки»** выполняются функциями и полями базы, а не
только кодом панели. Если обновлялась только статическая часть сайта, в
Supabase нужно по порядку выполнить целиком следующие файлы:

1. [`supabase/profiles.sql`](../supabase/profiles.sql)
2. [`supabase/site-data.sql`](../supabase/site-data.sql)
3. [`supabase/rich-forum.sql`](../supabase/rich-forum.sql)
4. [`supabase/chats.sql`](../supabase/chats.sql)
5. [`supabase/leaders.sql`](../supabase/leaders.sql)
6. [`supabase/nicks-verified.sql`](../supabase/nicks-verified.sql)

Каждый файл можно выполнить повторно. В частности, ошибка
`column "leader_of" of relation "forum_users" does not exist` означает, что
не выполнен пункт 5: он добавляет колонку `leader_of`, синхронизацию статуса
лидера и функцию кнопки «Сделать лидером». После выполнения перезайдите в
админ-панель и повторите действие.

Как это устроено:

- **Создаёт чат лидер альянса.** Отметку «лидер» ставит владелец в панели,
  вкладка «Игроки» → «Сделать лидером». Это не роль сайта, а доверие своему
  альянсу. Модерация тоже может создавать чаты.
- **Вступают по коду приглашения.** Лидер жмёт «Пригласить» в чате, копирует
  ссылку `#/chats/join/<код>` или диктует восемь символов. Если код утёк —
  «Сменить код», старый перестаёт работать.
- **Два вида:** альянсовый и межальянсовый. Разница только в подписи —
  в межальянсовый лидеры приводят своих людей тем же кодом.
- **До 200 человек** в чате — предел держит триггер в базе.
- **Видят только участники и модерация.** Об этом написано у входа в чат,
  скрытых от модерации чатов на сайте нет. В панели вкладка «Чаты»:
  список, участники, последние сообщения, закрыть/удалить/выгнать.
- **Новые сообщения** приходят опросом раз в 4 секунды, пока вкладка
  открыта. Это один дешёвый запрос; веб-сокеты и клиентская библиотека
  Supabase не нужны.

Чего в чатах нет намеренно: правки сообщений (сказанное сказано — есть
только удаление с причиной), реакций и вложений. Всё, что нужно оформить,
пишут на форуме, а в чат кидают ссылку.

## Как устроена модерация

**Списка запрещённых слов в проекте нет, и это решение, а не упущение.** Такой
список одновременно ловит невиновных (Кострома, Сукхотай, «нахимовский»)
и обходится одной точкой внутри слова. Он создаёт видимость модерации,
не давая её.

Поэтому смысл оценивает человек:

1. У каждой записи есть кнопка **«Пожаловаться»** с выбором пункта правил.
2. Жалобы попадают в панель, во вкладку **Жалобы**. Их видит только модерация:
   открытый список жалующихся сам стал бы инструментом травли.
3. Удаление всегда с указанием пункта. Автор видит не «удалено»,
   а «удалено по пункту 4».
4. Повторные нарушения — тишина на срок или запрет писать, вкладка **Игроки**.

Удалённый пост **не исчезает**: на его месте остаётся заглушка с причиной.
Молча пропавший пост читается как поломка сайта и порождает второй такой же,
а причина — единственное, чем правило вообще чему-то учит.

## Выдержка и «не прочитано»

**Выдержка** — правило «не чаще, чем». Без него один человек за вечер
заваливает ленту копиями одной темы, а ответы на спор превращаются в стену
из повторяющегося текста. Числа такие:

| Что | Сколько |
|---|---|
| Новых тем | 3 за 20 минут |
| Ответов | 8 за 2 минуты |
| Повтор того же текста (тема или ответ) | 10 минут |
| Владелец и модератор | втрое больше |

Три вещи про это правило стоит знать заранее:

- Держит его **база** — триггеры `forum_posts_hold` и `forum_comments_hold`
  в [`supabase/20260925-spam-hold-and-topic-reads.sql`](../supabase/20260925-spam-hold-and-topic-reads.sql).
  Запрос, посланный мимо сайта, от тех же проверялок не отвертится.
- Те же числа лежат в `config.js` (`postHoldMax`, `postHoldMinutes`,
  `commentHoldMax`, `commentHoldMinutes`, `repeatHoldMinutes`) — только ради
  надписей: форма называет срок заранее, а не после отказа. Совпадение
  чисел в двух местах сторожит тест, поэтому менять надо в обоих.
- Списков запрещённых слов это не отменяет и не вводит: правило смотрит на
  частоту и на дословный повтор, а не на смысл. Смысл по-прежнему оценивает
  человек (см. «Как устроена модерация»).

**Знак «не прочитано»** — на карточке темы в ленте: сколько чужих ответов
появилось после того, как человек последний раз входил в эту тему. Свои
ответы и стёртые не считаются. Отметку о входе ставит сама страница при
открытии темы, функцией `forum_read_topic`, и хранится она в таблице
`forum_topic_reads` — по одной строке на пару «человек и тема».

Счётчик приносит отдельное представление `forum_topic_unread`, а не колонка
в большом `forum_post_list`: ленту оно не ломает — если представление
откажет, темы выйдут без знаков. Гостю считать нечего: отметки привязаны
к человеку.

Черновой режим (`source: 'local'` в `config.js`) повторяет оба правила тем же
текстом отказов — проверить их можно без базы.

## Фильтры в адресе страницы

Раздел, тег, порядок и поиск живут в адресе ленты:

```
#/forum?cat=vs&tag=guide&sort=top&q=гвард
```

Зачем это человеку, который не пишет код:

- ссылку на «Разбор VS, лучшее» можно кинуть в чат, и откроется именно этот
  вид ленты, а не пустая страница форума;
- кнопка «назад» из темы возвращает туда, где человек был, с его фильтрами;
- перезагрузка страницы не сбрасывает вид.

Три правила, которые нельзя нарушать при правках:

- **Ключи (`cat`, `tag`, `sort`, `q`) и значения неподвижны.** Значения — это
  id разделов и тегов из `src/forum/rules.js`, те же, что лежат в базе.
  Переименование обесценивает все разосланные ссылки: старая откроется обычной
  лентой, и никто не заметит подмены.
- **Дефолт в адрес не пишут.** «Все разделы, свежее» — это `#/forum` без
  хвоста; иначе каждая короткая ссылка обрастает четырьмя параметрами.
- **Чужой id в адресе — не ошибка.** Его не проверяют по списку и молча
  показывают обычную ленту: ссылка пятилетней давности обязана открыть форум,
  а не пустой экран.

Разбором адреса заняты две чистые функции в
[`src/forum/feed-url.js`](../src/forum/feed-url.js) — они работают без
браузера, и тест сверяет их в обе стороны: любой раздел, тег и порядок,
записанные в адрес, читаются обратно тем же состоянием. Сама лента подписывает
адрес в одном месте (`writeFilters` в `src/forum/mount.js`, вызывается при
каждом запросе новой страницы постов) и делает это через `replaceState`, а не
через смену хэша: смена хэша перезапустила бы страницу, и человек потерял бы
прокрутку вместе с набранным в поиске словом.

## Отметка «проверен / устарел» у гайдов

Гайд отличается от темы форума тем, что его читают позже: совет, верный в
сентябре, после январского обновления может приносить убыток. Отметка модерации
говорит об этом до того, как человек долистал до конца.

Работает так:

- у гайда есть одно из трёх состояний — **нет отметки**, **проверен
  модерацией**, **устарел**; у первых двух страниц показывает дату решения и
  пояснение модератора;
- отметку ставит **только модерация** (кнопки «Проверен», «Устарел», «Снять
  отметку» внизу страницы гайда). Автору она недоступна, даже если гайд его:
  иначе «Проверено модерацией» стояло бы под каждым собственным текстом;
- игрок, который заметил, что совет перестал работать, жмёт «Сообщить, что
  гайд устарел» и пишет, что именно сломалось (5–280 символов). Один человек —
  один сигнал: повтор уточняет прошлый текст, а не добавляет строку;
- модератор видит список открытых сигналов под гайдом. Отметка закрывает их —
  разбор не должен вечно висеть в очереди.

Чего здесь намеренно нет:

- **Автоматического устаревания по дате.** Просмотрев три месяца без правок,
  гайд может оставаться безошибочным, а написанный вчера — не работать вовсе.
  Отметка, которую никто не ставил, была бы враньём, поэтому дата публикации
  ни на что не влияет;
- **Публичного счётчика недовольных.** Сигналы приватны: игроку видно только
  своё, остальное — модерации (политика `forum_guide_signals_read`). Список
  «кто сообщил об устаревании» читается как список недовольных, а адресом у
  этого сообщения нет.

## Срок действия темы

«Набор в альянс открыт» — это обещание, и через месяц оно перестаёт быть
правдой. Читатель, пришедший по такой теме в закрытый набор, делает вывод, что
форуму верить нельзя, — поэтому тема знает, до какого числа она актуальна.

Правило короткое:

- метка **«Набор»** или **«Срочно»** обязывает тему иметь срок. У остальных тем
  срок по желанию: «разбор актуален до патча» стареет по тем же часам;
- ставят срок вперёд **не меньше чем на сутки и не больше чем на 90 дней**;
  форма предлагает 3, 7, 14 и 30 дней, а при выборе метки срок подставляется
  сам (набор — 14 дней, срочный сигнал — 3);
- верхняя граница нужна не для порядка: без неё «срок» превращается в способ
  молча сделать тему вечной, и правило обходится одним кликом.

Истёкшая тема **не исчезает из ленты**, она получает метку «срок вышел». Соседний
проект прячет такие объявления с доски, но у нас под темой висит обсуждение:
вместе с объявлением пропали бы ответы людей. Плюс история сервера — «кто и
когда набирал альянс» — справочная информация, и вычёркивать её из поиска
незачем.

Продлить срок может автор темы и модерация: в открытой теме под текстом лежат
кнопки «+3 дня» … «+30 дней» и «Бессрочно» (последней нет у тем с обязательным
сроком). Отсчёт идёт от сегодняшнего дня, а не от прежней даты: продление темы,
проспавшей месяц, дало бы иначе пару дней вместо месяца.

Код: колонка, метка `sos` и триггер `forum_posts_expiry` — в
[`supabase/20260925-announcement-expiry.sql`](../supabase/20260925-announcement-expiry.sql);
та же миграция пересоздаёт представление `forum_post_list`, иначе лента не
увидит новую колонку (см. «Важно про представление» в этом же файле).
Чтение и продление — `setExpiry` в обоих адаптерах, поле формы и метки —
`renderExpiryField`, `expiryBadge`, `expiryControl` в
[`src/pages/forum.js`](../src/pages/forum.js), отправка и кнопки — в
[`src/forum/mount.js`](../src/forum/mount.js), список меток — `EXPIRY_TAG_IDS` и
`needsExpiry` в [`src/forum/rules.js`](../src/forum/rules.js). Границы срока
(`expiryDaysMin`, `expiryDaysMax`, `expiryChoices`, `expiryDefaultDays`) лежат
в `config.js` и повторяются в триггере — совпадение сторожит тест.

## Оспаривание запрета писать

Запрет писем и «тишина» отнимают у человека единственное средство связи с
модерацией: в чужой теме он не ответит, жаловаться не на что, а молча
пропавший доступ читается как поломка сайта. Поэтому у игрока под мерой
остаётся одна дверь — **возразить по существу**, и она открыта даже под
запретом. Право возразить — это не право писать.

Правило короткое:

- оспорить можно **только запрет писем и тишину**; на удаление поста апелляции
  нет — там причина видна на месте заглушки, и спорить с пунктом правил
  нужно тем же сообщением модерации;
- текст заявки — **20–600 символов**, и в нём нужно назвать тему или ответ,
  из-за которого пришла мера: «несправедливо» модерация не читает;
- на одну меру — **одна открытая заявка**. Пока её не разобрали, вторую база не
  принимает, а после ответа по этому же вопросу новая заявка откроется
  **через 7 дней** (срок считает любое решение, и удовлетворённое тоже);
- **мера на время разбора остаётся**. Апелляция — просьба пересмотреть, а не
  кнопка «пока спорим — я пишу»; иначе каждая жаловалась бы до бесконечности;
- модератор обязан ответить **текстом от 10 до 600 символов** и выбрать
  «удовлетворить» или «отклонить». Пустой ответ не проходит, а удовлетворение
  снимает ровно ту меру, которую оспорили, — вторую он не тронет.

Чего здесь намеренно нет:

- **Публичного списка апелляций.** Игроку видно своё, модерации — всё
  (политика `forum_appeals_read`). Открытый список жалующихся читается как
  список недовольных и становится инструментом травли; ник ответившего
  модератора игроку тоже не показан — ему нужен ответ, а не состав очереди.
- **Права писать под запретом.** Столбец `forum_appeals` не имеет политик на
  запись вообще: `forum_can_write()` отказывает забаненному, и полагаться на
  политики было бы нельзя. Обе двери — функции `forum_open_appeal` и
  `forum_review_appeal`, объявленные `security definer` с зафиксированным
  `search_path = public`, закрытые от `anon` и открытые вошедшим.

Код: таблица, две функции и представление `forum_appeal_list` — в
[`supabase/20260925-sanction-appeal.sql`](../supabase/20260925-sanction-appeal.sql).
Миграция **не обязана** быть выполнена до пуша: очередь читается отдельным
запросом, лента без неё живёт как жила, а панель модерации по отказу сама
называет имя файла, которое владельцу нужно прогнать в SQL Editor.
Двери — `openAppeal`, `reviewAppeal`, `listAppeals` в обоих адаптерах
([`src/forum/adapters/supabase.js`](../src/forum/adapters/supabase.js) и их
черновые двойники в `local.js`), форма под мерой — `renderSanctions` в
[`src/pages/forum.js`](../src/pages/forum.js), отправка — `sendAppeal` в
[`src/forum/mount.js`](../src/forum/mount.js), очередь модерации —
`renderAppeals` и `reviewAppealRequest` во вкладке **Жалобы** панели. Числа
(`appealMessageMin`, `appealMessageMax`, `appealAnswerMin`, `appealAnswerMax`,
`appealCooldownDays`) лежат в `config.js` и повторяются проверками таблицы —
совпадение и одинаковый wording отказов сторожит тест.

## Тишина в одном разделе

Общая тишина и бан отнимают форум целиком, и из-за одного разгоревшегося спора
в «Разборе VS» человек лишается ещё и вопросов, где он полезен. Модератор это
чувствует — и чаще не выбирает ничего. Третья мера оставляет ему соразмерный
ответ: **закрыть один раздел**, остальной форум открыт.

Правило короткое:

- тишина налагается **парой «игрок и раздел»**: второй строки на тот же раздел
  не бывает, продление — та же запись;
- срок — **от 1 до 30 дней**. Дольше держит только общий запрет, и это не
  придирка к цифре: «мьют до Нового года» — тот же бан, только без двери;
- пояснение **от 5 до 200 символов** обязательно и показывается игроку — и в
  уведомлении, и списком под его именем;
- закрытый раздел отнимает **текст**: новые темы и новые ответы. Реакции,
  жалобы и правка своего старого поста остаются — они не продолжают спор
  словами;
- игрок видит закрытый раздел **до отказа**: строка в списке разделов помечена
  «вам здесь нельзя», а под именем лежит список своих тишин со сроком и
  причиной. Молча получить отказ в момент отправки — значит решить, что сломан
  сайт.

Чего здесь намеренно нет:

- **Закрытия последнего открытого раздела.** База такой ход отвергает: сумма
  частных тишин стала бы общим запретом, замаскированным под частный. Общий
  запрет оспорим, а у молчания по разделам двери апелляции нет, и модератор,
  закрывший всё по очереди, отнял бы у человека право возразить. Панели остаётся
  наложить общую меру — там дверь есть.
- **Своего списка чисел в `config.js`.** Границы срока и длины пояснения держит
  функция в базе, а клиент и панель их только пересказывают; в черновом режиме
  те же числа записаны в `local.js` теми же словами отказа — совпадение
  сторожит тест.

Код: таблица `forum_section_mutes`, перегруженная `forum_can_write(p_category)`,
триггер слов отказа `forum_section_mute_guard` и дверь модерации
`forum_set_section_mute` — в
[`supabase/20260925-section-mute.sql`](../supabase/20260925-section-mute.sql).
Миграция **не обязана** быть выполнена до пуша: список тишин читается отдельным
запросом, а без таблицы лента и панель живут как жили (панель по отказу называет
имя файла). Пока файл не выполнен, в базе стоят прежние политики вставки и
прежняя `forum_can_write()` без аргумента — право писать не меняется ни на йоту,
и «закрытого раздела» никто не увидит просто потому, что закрывать нечего.

Двери — `listSectionMutes`, `setSectionMute`, `clearSectionMute` в обоих
адаптерах; разметка игрока — `renderSectionMutes` и `sectionMuteOf` в
[`src/pages/forum.js`](../src/pages/forum.js), чтение списка — `loadFeed` в
[`src/forum/mount.js`](../src/forum/mount.js). В панели мера живёт рядом с
общей ([`src/admin/screens/players.js`](../src/admin/screens/players.js) —
свёрнутый блок под пояснением про тишину), а решение попадает в журнал
модерации подписями «закрыл раздел» и «открыл раздел».

## Календарь встреч

Договориться о встрече в ленте нельзя: обсуждение идёт неделями, а «во сколько»
тонет между ответами. У встречи есть три вещи, которых у обсуждения нет — момент,
число участников и напоминание, — и ради них заведена отдельная страница.

Правило короткое:

- **встреча — это обычная тема** с меткой «Событие» и колонкой `event_at`.
  Отдельной таблицы событий нет намеренно: вместе с меткой у встречи уже живут
  обсуждение, реакции, жалобы, подписки, «не прочитано», выдержка и право
  оспорить удаление;
- **дата обязана быть при метке**: без `event_at` тема не проходит, а стоит снять
  метку — дата снимается сама. Иначе в календаре копились бы темы «когда-нибудь»;
- момент назначают **вперёд**: не меньше чем через 10 минут и не дальше 90 дней.
  Прошедшая встреча остаётся в списке завершённой и ответа не принимает;
- отвечают **тремя словами**: «буду», «возможно», «не приду». Пара «тема и
  человек» одна, поэтому передумать — та же запись, а «не приду» не удавляет её,
  освобождает место;
- **ответ не требует права писать**: забаненный человек не спорит словами, но
  может прийти на рейд. Тот же смысл, что у апелляций;
- **места считает база**: лимит лежит в теме, «буду» занимает место внутри одной
  операции с блокировкой темы, а «возможно» места не держит — иначе организатор
  заполнил бы встречу людьми, которые могут и не прийти;
- **отмена — это удаление темы**: своей пометки «отменено» нет, иначе у одной
  темы было бы две причины исчезнуть;
- **напоминание ставит себе сам игрок** — за 15 минут, за час или за сутки, и
  только на «буду» и «возможно». Оно приходит в общую лентку уведомлений,
  отдельного канала не заводим;
- **участников наружу не показывают**: страница называет только числа. Список
  придящих читается как карта составов альянса, а число мест публично. Ведущий
  виден — он и так публичен.

Чего здесь намеренно нет:

- **Своей сущности «событие» с отдельными комментариями и лайками.** Половина
  пользы календаря в том, что обсуждение встречи остаётся там же, где всегда,
  а не заводится вторым местом.
- **Своего списка чисел в `config.js`.** Границы держит миграция, клиент их
  только пересказывает, а в черновом режиме те же числа записаны в `local.js`
  теми же словами отказа — совпадение сторожит тест.
- **Длительности встречи у файла `.ics`.** Тема знает только момент, поэтому
  файл описывает точку во времени, а не выдуманное «+2 часа».

Код: колонки `event_at` и `event_capacity`, триггер `forum_posts_event_at`,
таблица `forum_event_rsvps`, представления `forum_event_list` и пересозданный
`forum_post_list` (с `my_rsvp` и `my_remind_minutes`), функции
`forum_answer_event`, `forum_event_going`, `forum_event_maybe` и
`forum_send_event_reminders` — в
[`supabase/20260925-event-rsvp.sql`](../supabase/20260925-event-rsvp.sql).
Напоминания носит планировщик: Supabase → Database → Cron → задача с выражением
`*/15 * * * *` и командой `select public.forum_send_event_reminders();` (тот же
способ, что у еженедельного дайджеста). Без задачи календарь, ответы и лимит
мест работают, а колокольник о встрече молчит.

Миграция **не обязана** быть выполнена до пуша: страница календаря читает
представление отдельным запросом, и без таблицы вместо пустого списка говорит
прямо — «прогоните 20260925-event-rsvp.sql». Лента тем от неё не зависит.
Правило про «пересоздать представление» здесь повторилось: `forum_post_list`

Двери — `listEvents`, `answerEvent`, `setEventAt` в обоих адаптерах; разметка —
`renderCalendar`, `eventActions` и `eventBadge` в
[`src/pages/calendar.js`](../src/pages/calendar.js), поведение —

раскрытая форма с отмеченной меткой живёт в состоянии, а не на экране: стартовый
кадр пересобирается, когда приезжают данные сайта.

## Забытый пароль

Письма «восстановить пароль» не существует, потому что почты не существует.
Вместо него игрок восстанавливает доступ сам: на странице входа — шаг
«Забыли пароль?», сайт выдаёт ключ сохранения, и через 12 часов заявка
принимает новый пароль сама, без чьего-либо подтверждения. Новый пароль
человек вводит сам.

Ни один пароль при этом не становится чужим. Ключ генерируется в браузере,
с него берётся отпечаток SHA-256, и в базу уходит только отпечаток. Новый
пароль игрок набирает в своём поле, а функция, которая его записывает, ничего
не возвращает — показать пароль владельцу негде. Раньше пароль придумывал
владелец и знал его навсегда: заменить его было негде, и «передать человеку
сразу» означало, что двоим известен один и тот же пароль.

Выдержка держится не на слове, а в базе: срок отсчитывается от `created_at`
заявки, и право поставить пароль функция сверяет по часам сервера. Часы
браузера тут ни на что не влияют — можно подкрутить их и увидеть форму на
минуту раньше, но база запрос всё равно отклонит. Повторная заявка отсчитывает
12 часов заново, поэтому потерянный ключ не получает уже отлежанное окно.

Заявка живёт неделю, открытой держится только одна: повторный шаг перезаписывает
прошлый ключ. Больше трёх заявок в сутки от одного игрока база не принимает —
иначе ожидание превратилось бы в машинное пережидание срока.

Дверь больше не держит живой человек, и это принято осознанно: игроку не нужно
ловить владельца на сайте. У владельца остаётся право решить, кого НЕ пускать, —
«Отклонить» в панели закрывает заявку навсегда, даже после истечения срока.
Отклонять может только владелец: права на форуме — отдельная учётная запись, и
токен GitHub, которым открыта панель, над форумом не властен. Проверяет это сама
база, а не страница.

## Что делать, если Supabase однажды отвалится

То же, что и с данными сайта: `source` в `config.js` — точка переключения.
Форум разговаривает только с контрактом (`src/forum/contract.js`) и не знает,
где лежат посты. Новый адаптер рядом с существующими, одна строка в конфиге —
и переезд состоялся. Тест в блоке Q следит, чтобы оба адаптера реализовывали
контракт целиком, поэтому расхождение обнаружится при запуске тестов,
а не в день переезда.

## Проверить, что всё работает

```
node tests/contract.test.js
```

Блок **Q. Форум** проверяет показ чужого текста, правила, права в схеме
и экраны панели. Он же следит за тем, чтобы права на строки остались
включёнными: без них публичный ключ открывает таблицы целиком.

## Если что-то не так

Таблица частых случаев — в порядке, в котором они обычно встречаются.

| Что видно | В чём дело |
|---|---|
| На странице **API Keys** нет адреса проекта | Его там и нет: адрес живёт отдельно. Собери из адресной строки браузера (пункт 4.1) |
| В Data API адрес показан с `/rest/v1/` | Это путь к таблицам, а не адрес проекта. Нужен только корень — но скопируешь с хвостом, сайт отрежет его сам |
| «Форум не подключён» | В `config.js` пусто в `url` или `anonKey`, либо `source` остался `'local'` |
| «В config.js попал СЛУЖЕБНЫЙ ключ» | Скопирован `sb_secret_…` или `service_role`. Возьми публичный: `sb_publishable_…` или `anon` |
| При регистрации просит подтвердить почту | Не выключен **Confirm email** (пункт 2). Почты у нас нет, письмо не придёт |
| «Профиль не создан» | SQL-схема не выполнилась или прошла с ошибками. Запусти `supabase/schema.sql` целиком заново |
| `syntax error at or near` в конце схемы | Схему правили руками. Ничего в ней менять не надо: правка внутри комментария рвёт строку, и хвост становится SQL. Вставь файл заново, как есть |
| Русский ник не регистрируется, «invalid email format» | Старая версия кода. Обнови сайт: превращение ника в адрес исправлено |
| Лента пустая, хотя посты есть | Старая версия схемы. Запусти `supabase/schema.sql` заново |
| Регистрация прошла, но в `forum_users` пусто | Записи ушли в браузер: `source` всё ещё `'local'` |
| `0 rows affected` при выдаче роли | Ник не совпал. Ник форума — тот, что придумал при регистрации, а не логин GitHub. Посмотри написание в **Table Editor** → `forum_users` |
| В шапке чужой ник вместо своего | Старая версия кода: «кто я» определялось первой строкой таблицы, а администратору видны все. Обнови сайт |
| «more than one row returned by a subquery» при правке поста | Старая версия схемы. Запусти `supabase/schema.sql` заново |
| Вкладки «Жалобы» и «Игроки» пишут «токен GitHub здесь не действует» | Ты не вошёл на форуме в этом браузере. Права форума — отдельная учётная запись |
| Вкладки говорят «вы участник» | Роль выдана, но не перезашёл на сайте — она читается при входе |
| «База отказала: недостаточно прав» | Правила доступа работают как надо, а действие для этой роли не разрешено |
| Всё было и перестало | Проект заснул после 7 дней тишины. Открой панель Supabase, он проснётся |

Отдельно про самый неприятный случай: **если служебный ключ успел попасть
в коммит**, менять файл недостаточно — ключ остаётся в истории git и виден
любому. Надо зайти в Supabase → **Settings → API Keys** и отозвать его
(для `sb_secret_…` — удалить, для `service_role` — деактивировать legacy-ключи),
затем создать новый. Пока ключ не отозван, он рабочий.

## Что было сломано и почему это важно знать

Работоспособность проверялась на живой базе запросами, а не «на глаз». Это
выявило две поломки, которых не было видно ни в коде, ни в тестах.

**Русские ники не регистрировались.** Вход по нику устроен так, что ник
превращается в адрес почты. Система входа Supabase не принимает в адресе
ничего, кроме ASCII, поэтому «Ковыль» отваливался с ошибкой
`Unable to validate email address`. То есть регистрация не работала почти
для всех: аудитория играет под русскими никами, а сообщение об ошибке причину
не называло.

Теперь ник переводится в латиницу и к нему добавляется короткий отпечаток
точного ника: `Ковыль` → `kovyl-f3d8aa29@…`. Отпечаток нужен, чтобы разные
ники не сошлись в один адрес — иначе второй человек при входе попал бы
в чужую учётную запись. Сам ник в базе хранится русскими буквами, адрес
человек не видит никогда.

**Лента была пуста для всех.** Ник автора брался связью с таблицей профилей,
а читать профили разрешено только свой и только модерации — поэтому связь
выбрасывала из ленты все посты, кроме собственных. Выглядело это как «форум
пуст» при полной базе постов.

Открыть профили целиком было бы неправильно: там даты регистрации и запреты,
а публичный список «кто забанен» — готовый инструмент насмешек. Поэтому ник
теперь лежит копией в самой записи, и подставляет его база, а не браузер —
подделать чужой ник в посте по-прежнему нельзя.

Плата за копию: если однажды появится смена ника, старые посты придётся
обновлять отдельно. Смены ника пока нет.

**Что из этого следует для тебя.** Если ты уже выполнял `supabase/schema.sql`,
запусти его ещё раз — исправления придут вместе с ним, ничего не потеряется.

## Что ещё нашлось при проверке на живой базе

Три ошибки, найденные уже после первого подключения. Все три исправлены,
но полезно знать, чем они пахли — похожие грабли легко положить снова.

**Администратор видел на сайте чужой ник.** Запрос «кто я» брал первую строку
из таблицы профилей с расчётом на то, что права доступа и так отдадут только
свою. Для участника верно. Для администратора — нет: ему видны все профили,
иначе модерация не работала бы, и «первая строка» оказывалась произвольной,
на практике самой старой в таблице.

Ошибка была в подходе: вопрос «кто я» решался правами доступа вместо проверки
идентификатора. Теперь идентификатор берётся из токена сессии, и строка
запрашивается точным сравнением.

**Любая правка поста падала с ошибкой про подзапрос.** В правах на строки
стояло условие `pinned = (select pinned from forum_posts p where p.id = id)` —
попытка запретить автору закреплять свой пост. Postgres связал `id` без имени
таблицы с той же таблицей внутри подзапроса, условие превратилось
в `p.id = p.id`, подзапрос вернул все строки.

И здесь дело не в опечатке: права на строки отвечают на вопрос «можно ли
трогать эту строку», а не «какие поля разрешено менять». Второй вопрос теперь
решает триггер, где доступно прежнее значение и подзапрос не нужен вовсе.

**Модератор мог сделать себя администратором.** Профили правит модерация —
и роль тоже оказалась в этом списке. Значит любой модератор назначал себя
администратором, и разница между ролями исчезала. Теперь роль меняет только
администратор; заодно нельзя забанить администратора и нельзя снять роль
с последнего оставшегося — иначе форум остался бы без хозяина.

## Убрать пробные записи

После проверки в базе остаются пробные учётные записи и посты. Их надо убрать
не только для порядка: у каждой рабочий пароль, и знает его не только владелец
форума.

Обычным запросом их не стереть: политики запрещают удаление строк всем,
включая администратора — удаление на форуме это отметка с причиной,
а не стирание. Поэтому чистка делается один раз, руками, служебными правами
SQL-редактора.

Открой [`supabase/cleanup-test-data.sql`](../supabase/cleanup-test-data.sql),
замени `ТВОЙ_НИК` на свой и выполни в **SQL Editor**.

Запрос удаляет всех, кроме тебя, и всё, что они написали. Работает как одно
целое: если ник не найдётся, остановится и не удалит ничего.

В конце того же файла есть два запроса для проверки — выдели их и нажми **Run**.
Должна остаться одна учётная запись, твоя, с ролью `admin`, и ни одного поста.

**Порядок важен: сначала стань администратором (шаг 5), потом чистка.**
Наоборот нельзя — роль выдаётся по нику, а к этому моменту записи уже не будет.

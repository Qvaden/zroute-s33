# Где живёт сайт: хостинг, домен и сертификат

Документ нужен, чтобы вопросы «а почему не GitHub Pages?», «а зачем вообще
хостинг, если сайт статический?» и «что делать, если сайт перестал открываться?»
не всплывали заново. Он же — единственное место, где записана конфигурация DNS.

## Коротко

```
GitHub (исходники, история, правки) ──push──> Render (раздача файлов + TLS)
                                          └─> GitHub Pages (зеркало: боевой запас)
NicNames — регистрация домена и DNS-зона: A-запись смотрит на Render
Supabase — данные форума, админки, рейтингов (это не файлы)
```

Публиковать надо **одну** ссылку: `https://zroutehub.bond`. `www` существует
только для редиректа на неё.

## Почему не GitHub Pages

Не из-за удобства, а из-за сертификата. Pages умеет отдавать HTTPS на
кастомный домен, но сертификат для него должен выпустить сам GitHub. С
марта 2024 он делает это только оптовыми прогонами и не гарантирует выпуск
для новых доменов, а для редких TLD вроде `.bond` выпуск практически не
происходит никогда. Практически это выглядит так: домен настроен, ждёшь
сертификат, он не появляется. Проверено на себе.

> **Важно для того, кто правит сайт:** ждать возобновления выдачи сертификатов
> GitHub бессмысленно. Если `https://zroutehub.bond` снова показывает ошибку
> сертификата — надо чинить выдачу сертификата у того, кто терминирует TLS
> (сейчас это Render), а не возвращаться на Pages.

Диагноз всегда один и тот же: сам сайт из России доступен, блокировки нет —
ломается только TLS-рукопожатие. Проверить можно так (см. «Как диагностировать»).

Из этого следует разделение ролей, которое нельзя путать: **домен** на Pages
раздать в HTTPS невозможно, поэтому прод живёт на Render; **копия сайта** на
Pages работает прекрасно — под сертификатом `*.github.io`. Поэтому Pages в
проекте остался, но как зеркало с собственным адресом, а не как редирект на
домен (см. «Что настроено в GitHub Pages»).

## Почему не Cloudflare

Cloudflare — типичный совет для «бесплатного HTTPS на своём домене», но он
частично блокируется в РФ, то есть ровно противоречит главному требованию к
сайту: открываться без VPN. Поэтому ни прокси через Cloudflare, ни Workers.

Не путать с тем, что край отдачи Render отвечает заголовком `Server: cloudflare`:
это собственный CDN Рендера, который мы не настраивали и настроить не можем,
цепочка «браузер → Cloudflare → нас» здесь не появляется.

## Почему Render, и почему это бесплатно

Прежний раздатчик — Netlify — в конце сентября 2026 заморозил прод: месячные
кредиты команды кончились, два пуша в `main` получили статус `Skipped`. То есть
`git push` перестал означать «изменение на сайте», что убивает главный режим
работы над этим проектом.

Аккаунт Render уже держит Telegram-бота 24/7, и бесплатных **750 instance hours**
хватает ровно на него («часы тютелька в тютельку»). Поэтому критично, что сайт
раздаётся как **статический сайт**, а не как веб-сервис: часы экземпляров
тратят только веб-сервисы, статический сайт их не потребляет вовсе. Бот не
теряет ни часа. Единственный реальный потолок общего тарифа — трафик
(порядка 100 ГБ в месяц на всё пространство), и его стоит держать в голове:
справочник гайдов — 164 картинки на ~52 МБ, которые грузятся по требованию.

## Что настроено в Render

Конфигурация живёт не в интерфейсе, а в **`render.yaml`** в корне репозитория:
её нельзя потерять при пересоздании сервиса и нельзя незаметно поправить руками.

| Что | Значение |
|---|---|
| Сервис | Blueprint из `render.yaml`, имя `zroutehub`, тип — static site |
| Ветка | `main`, автодеплой по коммиту (Commit hook) |
| Build command | `'true'` — намеренный пустой шаг: без него Render по наличию `package.json` попытался бы что-то устанавливать |
| Publish directory | `./` — корень репозитория (`index.html` и `admin.html` лежат в нём, собранного каталога нет) |
| Заголовок `/sw.js` | `no-cache, no-store, must-revalidate` — объявлен в том же `render.yaml` |
| Домены | `zroutehub.bond` (основной) и `www.zroutehub.bond` → редирект на основной |
| TLS | Let's Encrypt, выпускает и продлевает сам Render; для домена без wildcard не нужны ни TXT-запись, ни `_acme-challenge` |
| Запасной адрес | `https://zroutehub.onrender.com` — живой URL того же прод-деплоя |

Настройки GitHub-приложения Render требуют внимания: экран *Install Render*
**заменяет** список репозиториев, а не дополняет его. Если выбрать там один
репозиторий, бот лишится доступа к своему. Правильно — *All repositories*
(или отметить оба).

## Что настроено в NicNames

Регистрация домена и DNS-зона остаются у NicNames; ничего не «переносится».

| Что | Значение |
|---|---|
| Name-Servers | **Free**: `ns10.nicnames.com`, `ns11.nicnames.com`, `ns12.nicnames.com` |
| `zroutehub.bond.` | `A` → `216.24.57.1`, TTL 3600 |
| `www.zroutehub.bond.` | `CNAME` → `zroutehub.onrender.com.`, TTL 3600 |
| AAAA, CAA | отсутствуют намеренно |

Два подводных камня, на которых уже попались:

1. **Редактор DNS-записей появляется только при Free Name-Servers.** Пока домен
   на *Custom* NS (например, на `dns1..4.p07.nsone.net` от прежнего хоста), зоны
   в панели просто нет — сначала переключение NS, потом записи. Вариант
   «No Name-Servers» не выбирать никогда: домен перестанет резолвиться.
2. **Значение A-записи берётся только из экрана Render** (*Add DNS records*,
   строка «For A records, use this target value: …»). Его нельзя подставлять по
   памяти или из документации — это адрес под конкретный аккаунт.

## Что настроено в GitHub Pages

Pages раздаёт тот же `main` по адресу `https://qvaden.github.io/zroute-s33/` —
бесплатно, без отдельного workflow, синхронно с пушем. Это **боевое зеркало**, а
не спящий запас: адрес живёт под нормальным сертификатом GitHub и не зависит ни
от домена `.bond`, ни от Render.

| Что | Значение |
|---|---|
| Источник | тот же репозиторий, ветка `main` (Pages включён, папка — корень) |
| Файл `CNAME` | **удалён из корня** — он заставлял Pages отвечать `301` на `zroutehub.bond` |
| Редирект со зеркала на домен | отсутствует намеренно |
| `_redirects` | их нет: на Pages они работают только при кастомном домене |
| `.nojekyll` | обязателен (без него Pages не отдаёт `_coerce.js`, а с ним адаптеры не грузятся) |

**Почему редиректа нет.** Пока `CNAME` лежал в репозитории, каждая попытка
открыть зеркало превращалась в переход на домен — то есть там, где домен не
открывается, не открывалось и зеркало. Запасная ступенька, которая ведёт на
основную, запасной не является. Цена: человек, перешедший по ссылке зеркала,
остаётся на `github.io` и в адресе, и в переписке. Это осознанно: старые ссылки
на `zroutehub.bond` никуда не деваются и продолжают вести на основной адрес
напрямую, через Render.

Зеркало видно игроку в двух местах, где иначе он видит только пустоту: в
объяснении долгого ожидания (`src/main.js`, `mirrorLinkHtml`) и на странице
отказа сервисного работника (`sw.js`, ссылка «Открыть запасной адрес сайта»).
Адрес зеркала в коде один и выводится из `github.owner` / `github.repo`
(`CONFIG.mirrorUrl`) — смена репозитория не оставляет второго адреса, который
надо вспомнить руками.

## После push

Ничего делать не нужно: пуш в `main` сам запускает сборку и деплой, изменения в
проде через минуту-другую. История и откат — вкладка **Deploys** сервиса, кнопка
*Rollback* у нужного деплоя. Ветка или PR сами по себе нигде не публикуются:
прод у статического сайта один — это `main`.

Правило `ignore` для бот-коммитов намеренно не настроено: `backup-from-db.yml`
пишет тот же `data/live.json`, что и `pull-data.yml`, то есть каждый коммит бота —
это актуальные данные, и их деплоить надо.

Проверить, что деплой дошёл, удобно на файле, который меняется вместе с пушем:
`https://zroutehub.bond/docs/HOSTING.md` отдаётся как есть, потому что публикуется
корень репозитория.

## Планировщики GitHub Actions

Прод — статический сайт, и все три рабочих по расписанию живут в Actions. Это
единственная серверная часть проекта, и она бесплатная.

- `pull-data.yml` — приносит данные игры в `data/live.json`;
- `backup-from-db.yml` — каждые два часа читает базу и кладёт копию в тот же
  репозиторий. У файла два читателя: резерв на случай потери базы и сайт,
  который показывает эту копию, когда до базы не дошли (см. «Пустая таблица
  больше не молчит» ниже);
- `store-feed.yml` — читает Google Play и App Store и кладёт в базу события и
  пост об обновлении. Подробно — «Фид магазина» в `docs/FORUM.md`.

У `store-feed.yml` два секрета: `STORE_FEED_NICK` и `STORE_FEED_PASSWORD`
(Repositor → Settings → Secrets and variables → Actions). Это вход обычной
учётной записи бота, а не служебный ключ базы: прав у него ровно столько,
сколько модерация выдала роли. Секреты заводятся один раз:
Repository → Settings → Secrets and variables → Actions → New repository secret.
**Секретов нет — запуск не падает**: он печатает
отчёт и пишет, что ничего не тронул. Так же ведёт себя и ручной прогон с
отмеченным «Только показать, ничего не писать» — им и проверяют разбор, прежде
чем верить посту на сайте. Магазин меняет вёрстку независимо от нас: журнал
отказа при таком прогоне печатает заголовки страницы и куски HTML вокруг нужного
места, и правки идут в `src/forum/feed.js`.

## Как диагностировать, что именно сломалось

Первое и главное: **на машинах с российской сетью системный DNS врёт** — 53 порт
по пути перехватывают и отдают устаревшие ответы. Поэтому смотреть надо через
DoH, глазами интернета:

- `https://dns.google/resolve?name=zroutehub.bond&type=A` — должен отдать
  `216.24.57.1`. `type=NS` покажет `ns10..12.nicnames.com`.
- `https://dns.google/resolve?name=www.zroutehub.bond&type=CNAME` →
  `zroutehub.onrender.com`.
- `https://api.certspotter.com/v1/issuances?domain=zroutehub.bond&includeDropped=true`
  — журнал выпусков сертификатов. Новая запись на сегодняшнюю дату = сертификат
  выпущен; это самый дешёвый способ отличить «ещё не успели» от «сломалось».

Разные DoH-серверы могут показывать разное: один ещё держит старый кэш. Это не
поломка, а признак того, что делегирование менялось недавно.

Второе: **открытая страница ничего не доказывает**. Зарегистрированный
сервис-воркер продолжает рисовать сайт из кэша, когда наружу не проходит ни
один запрос, — можно сутки наблюдать рабочий сайт при мёртвом TLS. Прежде чем
считать проверку пройденной, в консоли браузера:

```js
// снять воркер и кэш, потом дёргать сеть напрямую
const rs = await navigator.serviceWorker.getRegistrations();
for (const r of rs) await r.unregister();
for (const k of await caches.keys()) await caches.delete(k);
await (await fetch('/sw.js', { cache: 'reload' })).status;
```

И третья ловушка: запрос к `https://www.zroutehub.bond/…` **со страницы на
голом домене** падает с `Failed to fetch` из-за CORS (Render не отдаёт
`Access-Control-Allow-Origin`), а не из-за сертификата. `www` проверяют переходом
в адресной строке (он должен привести на `https://zroutehub.bond/…`) либо
запросом с `mode: 'no-cors'`, где успехом считается прозрачный ответ.

Признаки неисправностей:

| Симптом | Причина и что делать |
|---|---|
| `NET::ERR_CERT_COMMON_NAME_INVALID`, в сертификате `*.github.io` | DNS снова смотрит на Pages — проверить NS и A-запись в NicNames |
| Страница-заглушка Render или 404 на всех путях | сломан `staticPublishPath` в `render.yaml`: публикуется не корень |
| `Certificate Error` в Render сразу после правки DNS | сертификат ещё не выпущен: это состояние ожидания, а не авария. Выпуск занимает десятки минут и идёт через HTTP-валидацию на голом домене, поэтому **откатывать NS назад нельзя** — это прерывает выпуск. Перезапуск: Settings → Custom Domains → удалить домен и добавить заново |
| Часть игроков «видит старую версию» | залипший сервис-воркер: проверить заголовок `/sw.js` (см. «Что настроено в Render») |
| `git push` есть, а на сайте изменений нет | посмотреть Deploys в Render: `Skipped` → вопрос к тарифу, `Failed` → смотреть лог сборки |
| Белый экран «вечная загрузка» на одном телефоне, у других всё открыто | не блокировка, а устройство или его сеть: пройти по шагам раздела «Сайт не открывается с телефона» (запасной адрес, приватная вкладка, прокси-ускорение браузера, Приватный DNS) |
| Открывается `zroutehub.onrender.com`, но не `zroutehub.bond` | устаревший DNS на устройстве или перехват 53 порта: проверить через `https://dns.google/resolve?name=zroutehub.bond&type=A`, на телефоне — сменить сеть и выключить сторонний Приватный DNS |
| С VPN сайт грузится идеально, без VPN — бесконечная загрузка; GitHub при этом открывается всегда | режут не сайт, а путь к домену: DNS-ответ сети про `.bond` устарел или TLS обрывается по имени. Единственная дорога, которая не зависит от ни того, ни другого, — зеркало `https://qvaden.github.io/zroute-s33/`, см. «Что настроено в GitHub Pages» |
| Сайт открылся — оболочки видно, — но рейтинг без цифр, а форум не прогружается | дело не в хостинге: не дошёл единственный запрос в базу. Адрес `*.supabase.co` отдаёт Cloudflare, и российские сети без VPN режут его точечно. Сайт в этом случае сам пишет «Показан снимок таблицы от …» — значит на экране копия двухчасовой давности, а не живые данные. Проверить тем же телефоном без VPN: открыть `https://ebumybzkrhhyinpjpeuk.supabase.co/rest/v1/`. Текст вместо вечной загрузки = путь к базе жив, и виноват прокси-ускорение браузера (шаг 4 ниже) |

## Сайт не открывается с телефона

Жалоба этого вида была такой: «по Wi-Fi с телефона — бесконечная загрузка и
белый экран, по мобильному интернету — не грузит вовсе; в целом доступа из РФ
нет». Проверили измерением, а не мнением, и он не подтвердился:

- `zroutehub.bond` резолвится в `216.24.57.1` из шести российских сетей
  (проверка шла через DoH, потому что системный DNS на этих сетях врёт);
- `https://zroutehub.bond/` отвечает `200` из Москвы, сертификат в журнале
  выпусков на месте;
- `https://zroutehub.onrender.com` (тот же прод без домена) — `200`;
- адреса базы, счётчика посещений и шрифтов достижимы.

Оговорка к последнему пункту, и она важна: проверка с этого компьютера шла
через **включённый VPN**, у которого он включён всегда. Значит эти три строки
доказывают только то, что адреса живы вообще, и ничего не доказывают про
доступ без VPN. Именно поэтому жалоба «без VPN рейтинг пустой, с VPN — всё
окно» не опровергается этим списком: база за Cloudflare, и её адрес могут
резать точечно, пока оболочка на GitHub и Render приходит нормально.

Значит общей блокировки нет: проблема точечная — её создаёт либо само
устройство, либо конкретная сеть. Есть и более острая версия той же жалобы:
«с VPN грузит идеально, без VPN — ужасно, а GitHub открывается всегда». Тогда
подозревать надо не хостинг, а путь к домену: DNS-про `.bond` в этой сети
врёт, а TLS по имени обрывается. Проверить это можно одним адресом —
зеркалом на GitHub, которое живёт под сертификатом GitHub и не зависит ни от
домена, ни от Render: `https://qvaden.github.io/zroute-s33/`.

Порядок действий для человека без инструментов (с телефона, шаг за шагом):

1. **Открыть запасной адрес** `https://zroutehub.onrender.com`. Открылся — сайт
   жив, и дальше разговор только про DNS/сертификат/прокси на устройстве. Не
   открылся и там — это хостинг, смотреть Deploys в Render.
2. **Открыть зеркало** `https://qvaden.github.io/zroute-s33/`. Работает там,
   где не работает ни домен, ни `onrender.com`: режет тогда не хостинг, а путь
   к нашему домену в конкретной сети. Содержимое то же самое, включая форум и
   вход — данные берутся из одной базы.
3. **Открыть в приватной вкладке** (Chrome: меню → «Новая вкладка в режиме
  Incognito»). Приватная вкладка не использует сервис-воркер и кэш обычного
   окна, поэтому она отделяет «сломана раздача» от «залипла копия на устройстве».
4. **Выключить прокси-ускорение браузера.** Это самый частый источник именно
   белого экрана в РФ: режим «Экономия трафика» / «Turbo» в Chrome и Яндекс.
   Браузере и «Маскировка IP-адреса» в Safari на iOS гонят страницы через чужой
   сервер, и тот сервер сайт не достанет.
   - Chrome: меню → Настройки → «Просмотр и загрузка страниц» → «Экономия
     трафика» — выключить.
   - Safari (iPhone): Настройки телефона → Safari (или «Apple ID → iCloud →
     Приватный relay») → «Маскировка IP-адреса» → «Закрыт».
   - Android, Настройки → «Беспроводные сети» → «Дополнительно» → «Приватный
     DNS» → «Выключен» (или «Автоматический»). Сторонний провайдер вроде
     `dns.adguard.com` обрывает половину адреса и сайт выглядит мёртвым.
5. **Сменить сеть**: мобильный интернет вместо Wi-Fi и обратно. Гостевой и
   корпоративный Wi-Fi с входной страницей перехватывают запросы — на такой
   сети белый экран означает «сначала войдите на их странице».
6. **Стереть копию сайта на устройстве**, если помог шаг 3: Chrome → Настройки →
   «Конфиденциальность и безопасность» → «Очистить данные просмотров» → отметить
   «Изображения и другие файлы, сохранённые в кэше» → «Очистить данные».

Что сделано на стороне раздачи, чтобы эти случаи не выглядели как «сайт умер»:

- **Сеть больше не ждут вечно.** В [`sw.js`](../sw.js) запрос ждать
  `NETWORK_WAIT_MS` (5 секунд), и если для него есть сохранённая копия —
  страница отдаёт её вместо белого экрана. Без сохранённой копии ожидание
  остаётся прежним: обрывать первое в жизни открытие нечем.
- **Отказ назван словами.** Переход по адресу без сети и без копии теперь
  получает маленькую русскую страницу «Сайт не открылся» с причиной, советом
  сменить сеть и кнопкой «Повторить», а не типовую системную заглушку.
- **Панель и база по-прежнему проходят мимо кэша**, а `/sw.js` отдаётся с
  `no-store` — залипшая версия не может стать причиной «у всех работает, у
  одного нет».
- **Долгое ожидание данных называют вслух.** Таблица результатов лежит в базе,
  а база на бесплатном тарифе засыпает и просыпается десятью секундами. Через
  `CONFIG.slowBootSeconds` (9) страница перестаёт крутить «Загружаем данные…» и
  говорит причину, предлагает «Повторить» и напоминает, что форум, календарь,
  справочник и обновления этих данных не ждут.
- **Пустая таблица больше не молчит.** Когда запрос в базу не дошёл, сайт
  читает `data/live.json` — копию тех же данных, которую воркфлоу
  `backup-from-db.yml` обновляет каждые два часа, — и пишет сверху полоску
  «Показан снимок таблицы от 30.09, 09:56». Файл лежит рядом со страницей под
  тем же адресом, поэтому если оболочка пришла, придут и данные. В полоске
  названо и то, чего копия не заменяет: форум, вход и новые посты живут только
  в живой базе. Если не ответил никто, полоска говорит «Данные не дошли» и
  приводит причину — вместо рейтинга без цифр. Разбирается в `loadAll()`
  (`src/data/index.js`) и `dataNotice()` (`src/main.js`).
  Побочный эффект тот же, что у остальных файлов сайта: ответ попадает в запас
  сервисного работника, поэтому без связи человек видит последнюю копию и её
  же час, а не пустоту.
  Оговорка про саму копию: она снимается с набора сервера сайта, и этот же
  набор показывает страница — выбора сервера у зрителя с 05.10.2026 нет. Поэтому
  «показан снимок» всегда означает снимок того, что человек ожидал увидеть. Если
  в `config.js` назовут другой сервер, копия до первого прогона
  `backup-from-db.mjs` останется старой: номер набора в ней не подписан, и
  глазами разницы не видно.
- **Запасной адрес показывается сам.** Ссылка на зеркало появляется в двух
  местах, где человек иначе видит только пустоту: в объяснении долгого ожидания
  данных и на странице отказа сервисного работника. Адрес выводится из
  `github.owner` / `github.repo` (`CONFIG.mirrorUrl`), поэтому переезд на другой
  репозиторий не оставляет в проекте второго адреса, который надо вспомнить.
- **Форум показывает прошлый экран сразу** (см. `docs/FORUM.md`, раздел
  «Плавный вход и память первого экрана»): на медленном соединении человек
  видит темы и строку «обновляем», а не пустоту.

Поведение раздачи на просрочке сети, отказе и пустом кэше проверяется тестами
(`tests/contract.test.js`, раздел «Раздача: сеть не держит белый экран») — они
исполняют вырезанное тело обработчика запроса с подставными сетью и кэшем.
Что пустая таблица обязательно подписана, сторожит раздел «Снимок вместо базы:
пустая таблица обязана быть подписана» — он исполняет вырезанный `loadAll()`
с подставными адаптерами и настоящую полоску с подставными узлами. Глазами
это не проверить: чтобы увидеть снимок, надо оказаться в сети, которая не
допускает до базы.

## Аварийный сценарий

Если Render станет недоступен (в том числе из-за блокировки его IP в РФ):

1. Быстро — в зоне NicNames поменять `A zroutehub.bond.` с `216.24.57.1` на
   адрес нового раздатчика и добавить `CNAME www` на него же. Сайт отдастся, но
   **HTTPS сломается**, пока новый хост не выпустит сертификат под домен. Это
   откат «чтобы работало», а не «как надо жить».
2. Совсем быстро — **ничего не менять в DNS**: зеркало
   `https://qvaden.github.io/zroute-s33/` живёт на том же `main` и отдаёт его со
   своим сертификатом. Менять надо только адрес, который раскидывают людям, и
   вставлять ссылку на домен внутрь зеркала.
3. Надёжно — `node scripts/build-preview.mjs` собирает весь сайт в один
   самодостаточный HTML-файл; его можно раздать с любого хостинга с нормальным
   сертификатом.
4. Данные не теряются ни при каком сценарии: они в Supabase, а ежедневные
   резервные копии коммитятся в репозиторий тем же workflow.

GitHub Pages сознательно **не** отключён: он бесплатен, синхронизируется сам и
раздаёт сайт прямо со своего адреса — то есть работает боевым зеркалом, а не
редиректом. Ссылки на `zroutehub.bond`, разбросанные по Discord, при этом не
меняются: их по-прежнему обслуживает Render.

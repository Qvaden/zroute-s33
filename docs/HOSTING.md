# Где живёт сайт: хостинг, домен и сертификат

Документ нужен, чтобы вопрос «а почему не GitHub Pages?» не всплывал заново.
Он же — инструкция по восстановлению после аварии.

## Коротко

```
GitHub (исходники, история, правки) ──push──> Netlify (раздача файлов + TLS)
                                          └─> GitHub Pages (зеркало, спит)
Supabase — данные форума, админки, рейтингов (это не файлы)
NicNames — только регистрация домена; DNS-зона перенесена в Netlify
```

Публиковать надо **одну** ссылку: `https://zroutehub.bond`.

## Почему не GitHub Pages

Не из-за удобства, а из-за сертификата. Pages умеет отдавать HTTPS на
кастомный домен, но сертификат для него должен выпустить сам GitHub. С
марта 2024 он делает это только оптовыми прогонами и не гарантирует выпуск
для новых доменов, а для редких TLD вроде `.bond` выпуск практически не
происходит никогда. Практически это выглядит так: домен настроен, ждёшь
сертификат, он не появляется. Проверено на себе.

> **Важно для того, кто правит сайт:** ждать возобновления выдачи сертификатов
> GitHub бессмысленно. Если `https://zroutehub.bond` снова показывает ошибку
> сертификата — надо чинить выдачу сертификата на стороне того, кто терминирует
> TLS (сейчас это Netlify), а не возвращаться на Pages.

Диагноз всегда один и тот же: сам сайт из России доступен, блокировки нет —
ломается только TLS-рукопожатие. Проверить можно так (см. «Как диагностировать»).

## Почему не Cloudflare

Cloudflare — типичный совет для «бесплатного HTTPS на своём домене», но он
частично блокируется в РФ, то есть ровно противоречит главному требованию к
сайту: открываться без VPN. Поэтому ни прокси через Cloudflare, ни Workers.

## Что настроено в Netlify (бесплатный тариф)

| Что | Значение |
|---|---|
| Проект | импортирован из GitHub, ветка `main` |
| Build command | пусто (сборки нет) |
| Publish directory | `/` — корень репозитория |
| Прод-домен | `zroutehub.bond` (primary) |
| `www` | редирект на primary |
| TLS-сертификат | выпущен Netlify 21.09.2026 (Let's Encrypt), SAN покрывает `zroutehub.bond` и `www.zroutehub.bond`, срок 90 дней, продлевается сам |
| Visitor access | production — публичный, Deploy Previews — приватные (`Customize` → `Private` → `Applies to: Previews only`) |
| Плашка «Powered by Netlify» | выключена в `Project configuration → Visitor access → Powered by Netlify badge` |
| DNS-зона | перенесена на Netlify: `dns1..4.p07.nsone.net` |

Делегирование NS — это **не** перенос домена: регистратор, владелец и
бесплатная регистрация остаются в NicNames.

Правило `ignore` для бот-коммитов намеренно не настроено: `backup-from-db.yml`
пишет тот же `data/live.json`, что и `pull-data.yml`, то есть каждый коммит
бота — это актуальные данные, и их деплоить надо.

## После push

Ничего делать не нужно: push в `main` сам запускает деплой, через ~15 секунд
изменения в проде. История и откат — `Deploys → Publish deploy`. Предпросмотр
ветки или PR — отдельный URL в уведомлении сборки, он доступен только после
входа в Netlify (см. Visitor access выше).

## Как диагностировать, что именно сломалось

Первое и главное: **на машинах с российской сетью системный DNS врёт** —
53 порт по пути перехватывают и отдают устаревшие ответы, а `--resolve`иногда игнорируется. Поэтому:

```bash
# состояние домена глазами интернета (не через локальный резолвер)
curl -s "https://cloudflare-dns.com/dns-query?name=zroutehub.bond&type=NS" -H "accept: application/dns-json"
curl -s "https://dns.google/resolve?name=zroutehub.bond&type=A"            -H "accept: application/dns-json"

# какой сертификат реально отдают, по IP из предыдущей команды
echo | openssl s_client -connect <IP-Netlify>:443 -servername zroutehub.bond 2>/dev/null \
  | openssl x509 -noout -subject -issuer -ext subjectAltName
```

Отвечают `185.199.108.153…111.153` — это GitHub Pages, то есть DNS снова туда
смотрит; `63.176.8.218` / `35.157.26.135` — Netlify. Разные DoH-серверы могут
показывать разное: один ещё держит старый кэш, и это не поломка, а признак
того, что делегирование недавно менялось. Наружу сайт сверять ещё через
`api.ssllabs.com`, иначе локальный кэш покажет `*.github.io` там, где уже всё
починено.

Признаки неисправностей:

| Симптом | Причина |
|---|---|
| `NET::ERR_CERT_COMMON_NAME_INVALID`, в сертификате `*.github.io` | DNS домена снова указывает на Pages — проверить NS |
| В сертификате `*.netlify.app` | домен на Netlify, но сертификат под домен ещё не выпущен; пнуть `Domains → HTTPS → Retry DNS verification` |
| Страница логина Netlify | в `Visitor access` прод стал `Private` |
| Открылся `http://`, а `https://` нет | сертификат не выпущен, см. строку выше |

## Аварийный сценарий

Если Netlify станет недоступен (в том числе из-за блокировки его IP в РФ):

1. Быстро — вернуть DNS на регистраторе: в панели NicNames в `Name-Servers`
   поставить `ns10.nicnames.com`, `ns11.nicnames.com`, `ns12.nicnames.com`.
   Сайт снова отдастся с GitHub Pages. **HTTPS при этом снова сломается** —
   это откат «чтобы работало», а не «как надо жить».
2. Надёжно — `node scripts/build-preview.mjs` собирает весь сайт в один
   самодостаточный HTML-файл; его можно раздать с любого хостинга с
   нормальным сертификатом.
3. Данные не теряются ни при каком сценарии: они в Supabase, а ежедневные
   резервные копии коммитятся в репозиторий тем же workflow.

GitHub Pages при этом сознательно **не** отключён: он бесплатен, синхронизируется
сам и даёт редирект `qvaden.github.io/zroute-s33/ → zroutehub.bond`, так что
старые ссылки, разбросанные по Discord, продолжают вести куда надо.

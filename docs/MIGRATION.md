# Переезд: сайт без GitHub

До этого документа сайт жил так: история сервера в `data/live.json`, панель
писала туда через API GitHub, вход по токену. Работало, но упиралось в две вещи.

**Два пароля.** Токен GitHub для панели, ник с паролем для форума. Две системы
прав, ничего не знающие друг о друге.

**Редактор был один.** Чтобы пустить второго человека, надо было выдать ему
доступ к репозиторию и объяснить, что такое personal access token — ради правки
счёта в VS. На практике этого никто не делал.

Теперь данные сайта живут в той же базе, что форум. Вход один, права выдаются
нажатием, GitHub из повседневной работы убран.

## Что нужно сделать

Порядок обязателен: каждый шаг опирается на предыдущий.

### 1. Схема профилей и вложений

Supabase → **SQL Editor** → **New query** → вставить целиком
[`supabase/applied/profiles.sql`](../supabase/applied/profiles.sql) → **Run**.

Добавляет аватарку, подпись и альянс в профиль, вложения к постам, хранилища
для картинок.

### 2. Схема данных сайта

Тем же способом — [`supabase/applied/site-data.sql`](../supabase/applied/site-data.sql).

Создаёт таблицы под историю сервера, права на них, журнал правок и функцию
`site_dataset`, которой сайт читает всё разом.

Ничего в файлах не правь. Они рассчитаны на повторный запуск: недостающее
добавляется, существующее не ломается.

### 3. Перенести историю

Это единственный шаг, который делается на компьютере:

```
node scripts/migrate-to-supabase.mjs
```

Скрипт читает `data/live.json` и печатает `dist/migrate.sql` — открой этот файл,
скопируй целиком, вставь в SQL Editor, **Run**.

Скрипт **не пишет в базу сам**, и это осознанно: для записи напрямую нужен
служебный ключ, дающий полный доступ ко всему. Ради одноразовой операции
пришлось бы где-то его держать — в переменной окружения, в истории команд.
Ключ живёт дольше задачи.

Проверить после запуска (запросы есть в конце файла):

```sql
select
  (select count(*) from public.site_alliances) as alliances,
  (select count(*) from public.site_weeks) as weeks,
  (select count(*) from public.site_results) as results;
```

Числа должны совпасть с теми, что скрипт напечатал в начале файла.

### 4. Переключить источник

В `config.js`:

```js
dataSource: 'supabase',   // было 'json'
```

Закоммитить и запушить. Через минуту сайт читает данные из базы.

### 5. Выдать себе право редактора

Ты администратор, поэтому право у тебя есть уже — у администратора оно
всегда. Отдельно выдавать не нужно.

Открой `admin.html`, войди **ником и паролем от форума**. Токен больше
не спрашивается.

### 6. Сервер у данных сайта (шаг мультиаренды)

Сделано 04.10.2026. Нужно, чтобы рейтинг, хронология и тексты перестали быть
одним набором на всю базу: форум уже живёт несколькими серверами, а данные сайта
сервера не знали.

Тем же способом — вставить целиком
[`supabase/applied/20261004-site-server-scope.sql`](../supabase/applied/20261004-site-server-scope.sql)
→ **Run**. Файл был прогнан до пуша кода, и вот почему порядок здесь не
формальность: новая панель и новый сайт спрашивают `site_dataset(p_server)`, а без
этого файла база такой функции не знает вовсе.

Что он делает: у пяти таблиц появляется колонка `server_id` (все существующие
строки получают 33-й сервер — других серверов у данных сайта до этого шага не
было), у недель, событий, текстов и результатов ключ становится парой «сервер и
id», а `site_dataset(p_server)` отдаёт набор одного сервера ровно той же формы,
что и прежде. Идентификатор альянса остаётся глобальным намеренно: на него
смотрят подписки дайджеста и турниры VS, и локальный id сделал бы каждую такую
строку двусмысленной.

Проверить прогон (ничего не меняет, читать можно сколько угодно раз):

```sql
select count(*) as alliances from public.site_alliances where server_id = 33;
select public.site_dataset(33);
```

Числа альянсов, недель и результатов должны остаться теми же, что до прогона, а
`site_dataset(33)` — отдать тот же набор, что и раньше. Проверка, что серверу
вообще есть что показать, тем же вызовом: `select public.site_dataset(44);` вернёт
пустые списки — это и есть состояние нового сервера, пока его модератор не внёс
первую неделю.

Чего в этом шаге нет, и это не забыто: права на внесение по серверу (модератор
одного сервера пока правит чужую неделю), переключатель сервера на самом сайте
(`?server=N` для вкладок рейтинга) и отдельный снимок `data/live.json` на каждый
сервер. Планировщик снимка шлёт вызов без аргумента и получает 33-й сервер, как
и раньше.

### 7. Закрыть гостю свободный номер альянса

Одна короткая правка после шага 6: живой вызов публичным ключом показал, что
`site_next_alliance_id()` доступна гостю. В файле шага стояло снятие права
только у `anon`, а Postgres при создании функции даёт EXECUTE роли `PUBLIC`, и
`anon` в неё входит — то есть право оставалось через наследие. Ничего опасного
гость этим не получает (число свободно созданного id, а записать его всё равно
не сможет), но панель эта функция не касается, и обещание реестра должно
соответствовать базе.

Вставить целиком
[`supabase/20261004-site-next-id-anon.sql`](../supabase/20261004-site-next-id-anon.sql)
→ **Run**. Две строки, ничего в данных не меняют.

Проверить можно прямо в браузере, без SQL-консоли: открыть сайт в режиме
инкогнито и посмотреть Network-вкладку — вызов `site_next_alliance_id` от гостя
обязан отвечать 401 «permission denied for function site_next_alliance_id».
Проще глазами: панель спрашивает этот номер только при создании альянса, и после
прогона она создаёт строки как раньше.

## Как теперь пустить второго редактора

1. Человек регистрируется на сайте, на вкладке **Форум**.
2. Говорит тебе свой ник.
3. Панель → **Игроки** → напротив его ника **«Сделать редактором»**.

Всё. Ни GitHub, ни токенов, ни доступа к репозиторию.

## Права: два независимых признака

| Признак | Что даёт | Кто выдаёт |
|---|---|---|
| `can_edit_site` | Править итоги VS, альянсы, хронологию, тексты | администратор |
| `role = moderator` | Разбирать жалобы, удалять чужие посты | администратор |
| `role = admin` | Всё вышеперечисленное плюс роли и пароли | вручную в SQL |

Признаки **независимы**, и это не упущение: вносящий результаты VS не обязан
разбирать споры, а модератор форума не обязан иметь доступ к истории сервера.
Слепить их в одну роль значило бы выдавать лишнее, чтобы дать нужное.

Три правила, которые база держит сама:

- роль меняет только администратор — иначе модератор назначил бы админом себя;
- администратора нельзя забанить — это способ отобрать форум у владельца;
- нельзя снять роль с последнего администратора — форум остался бы без хозяина.

## Что заменило историю git

В репозитории журнал правок вёлся сам: каждый коммит — кто и что поменял.
База так не умеет, поэтому вместо него два механизма.

**Таблица `site_audit`.** Заполняется **триггерами**, а не панелью: правка
из SQL-редактора или чужим скриптом всё равно попадёт в журнал. Панель могла бы
забыть записать — и именно тогда журнал нужнее всего.

**Выгрузка в репозиторий каждые два часа.** Воркфлоу
[`backup-from-db.yml`](../.github/workflows/backup-from-db.yml) читает базу и
кладёт в `data/live.json`. Интервал выбран не ради резерва: с 01.10.2026 этот
файл читает и сайт, когда до базы не дошли (см. «Запасное чтение» в
`docs/ARCHITECTURE.md`), а копия суточной давности для этой роли не годится.

Это не «на всякий случай», а условие переезда. Пока история лежала в git,
ей не могло случиться ничего. В базе аккаунт можно потерять, тариф изменить,
а неудачный запрос стирает данные молча. С выгрузкой потерять можно максимум
два часа правок.

У скрипта два предохранителя, без которых он был бы опаснее своего отсутствия:
пустой ответ базы считается отказом, и потеря больше половины альянсов — тоже.
Записать пустоту поверх копии значило бы затереть историю ровно тогда, когда
она нужнее всего.

## Путь назад

Если Supabase однажды окажется неприемлем, возврат — одна строка:

```js
dataSource: 'json',
```

`data/live.json` лежит в репозитории и обновляется каждые два часа, так что
вернётесь к состоянию не старше двух часов. Форум при этом останется в базе
или отключится (`forum.source: 'local'`), а рейтинг, хронология и гайды
заработают как прежде.

Это то самое свойство, ради которого в проекте с самого начала есть адаптеры
(см. [ARCHITECTURE.md](./ARCHITECTURE.md)): переезд стоит выходных, а не
переписывания.

## Если что-то не так

| Что видно | В чём дело |
|---|---|
| «Не найдена функция site_dataset» | Не выполнен `supabase/applied/site-data.sql` |
| «…find the function public.site_dataset(p_server)» | Функция без параметра в базе есть, а с параметра — нет: не выполнен шаг 6, `supabase/applied/20261004-site-server-scope.sql` |
| «База не отдала данные сайта» | Не выполнен `supabase/applied/site-data.sql` или `supabase/applied/20261004-site-server-scope.sql` — текст ошибки называет оба |
| «В config.js не заполнен server» | Панель не знает, чьи данные править: в `config.js` должно быть число, например `server: 33` |
| Панель просит токен GitHub | Старая версия кода, обнови страницу через Ctrl+Shift+R |
| «Нет права редактора» | Право не выдано. Администратор → Игроки → «Сделать редактором» |
| Сайт пустой, а в базе данные есть | В `config.js` остался `dataSource: 'json'` |
| «База отказала: недостаточно прав» | Правила доступа работают верно, а действие этой роли не разрешено |
| Выгрузка падает с «пустой набор» | Предохранитель сработал: проверь базу, копию он не тронул |
